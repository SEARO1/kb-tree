# Plan: Reduce layout complexity for cyclic KB graph

## Goal
Make the graph readable without losing real transition semantics from the KB (including loops/cycles).

## Assessment of the proposed solution
1. **"Rabbit-tortoise algorithm to find cyclic graph" is not suitable here**
   - Floyd’s rabbit-tortoise cycle detection assumes a **single next pointer** (linked-list / functional graph).
   - This graph is a **general directed graph** with multiple outgoing edges per node (`parseKB.ts` builds adjacency maps with many targets), so Floyd cannot correctly identify all cycles/components.
2. **"Switch cyclic to acyclic" can harm meaning if done literally**
   - Converting the actual data graph to acyclic by removing edges changes business flow semantics.
   - Better approach: create a **layout-time acyclic abstraction** while preserving original edges in rendering.
3. **Conclusion**
   - The idea is directionally correct (handle cycles before layout), but algorithm choice and transformation strategy should be replaced.

## Better approach (recommended)
Use **SCC condensation + hierarchical layout + progressive detail**.

### Phase 1: Build cycle-aware structure
1. In `src/components/parseKB.ts`, after adjacency is built, run **Tarjan SCC** (or Kosaraju) on intent graph.
2. Group each strongly connected component (SCC):
   - SCC size = 1 and no self-loop => acyclic singleton
   - SCC size > 1 or self-loop => cyclic component
3. Build a **condensed DAG** where each SCC is a super-node.

### Phase 2: Layout strategy
1. Run ELK layered layout on the **condensed DAG** (not the raw graph).
2. For each cyclic SCC super-node:
   - Expand members with local layout (circle/force/small layered) inside a bounded box.
   - Keep internal cycle edges visible but subtle.
3. For inter-SCC edges:
   - Route from SCC boundary ports to reduce crossings.

### Phase 3: Rendering and interaction
1. Keep full-fidelity original edges, but add classes:
   - `intra-scc` (inside cycle),
   - `inter-scc` (between components),
   - `back-edge` (optional semantic style).
2. Default view = simplified:
   - collapse SCC clusters initially,
   - expand on click for details.
3. Add edge de-noising controls:
   - hide low-priority edge labels at low zoom,
   - optional filter by method (`dtmf`, `followUp`, `redirect`, etc.),
   - fade non-neighbor edges when a node/edge is focused (already partially present in `Canvas.tsx`).

## Why this fits current code
- `parseKB.ts` already centralizes graph construction and has adjacency/inbound/outbound counts, so SCC computation naturally fits there.
- `Canvas.tsx` already applies ELK and style overlays; this is the right place to add cluster rendering/expand-collapse behavior.
- Existing split-node logic for high-degree intents can be retained as a secondary tactic, but SCC condensation should be the primary complexity reducer.

## Concrete implementation plan
1. **Graph analysis utilities (`parseKB.ts`)**
   - Add `computeSCCs(adjacency)` utility.
   - Add `buildCondensedDag(sccResult)` utility.
   - Extend return shape (or metadata) with:
     - node -> sccId map,
     - SCC members,
     - condensed edges.
2. **Layout model (`Canvas.tsx`)**
   - Layout condensed DAG first.
   - Expand SCC members relative to cluster anchor positions.
   - Style intra-SCC edges dashed/lower opacity.
3. **UI behavior (`Canvas.tsx` / `App.tsx`)**
   - Add toggle: `Simplified (clusters)` vs `Detailed`.
   - Add "expand selected cluster" interaction.
4. **Validation**
   - Compare before/after with same JSON:
     - edge crossing count (visual check),
     - average visible edge label overlap,
     - user path tracing time (manual smoke test).

## Expected outcome
- Significant reduction in long crossing lines in the global view.
- Cycles remain represented accurately (no semantic data loss).
- Users can progressively drill into complex cyclic regions instead of seeing all edges at once.
